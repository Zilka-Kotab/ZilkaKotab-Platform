## Office Action contact evidence

ODP Office Action PDFs are frequently image-only, even when they were generated electronically. An empty native text layer is not evidence that contact information is absent: use bounded OCR and disclose the sampled-page limits. Keep documents transient and persist only verified contact/provenance metadata.

**Why:** Live examiner actions yielded empty text extraction while OCR recovered the examiner-named telephone paragraph. That paragraph also includes a supervisor's number and help-desk details, which must not be assigned to the selected examiner.

**How to apply:** Assignment identifies candidate documents, not authorship. Verify the selected examiner in the actual contact block; stop before supervisor details and reject ambiguous addresses. Never reconstruct or “correct” an OCR address from an assumed name convention. Preserve document ID, application number, date, page and extraction method. Do not forward the ODP API key to download redirect hosts. Check the PDF library's installed types for cleanup semantics rather than assuming older PDF.js document methods still exist.

The Patent File Wrapper search endpoint accepts a patent number through the GET `q` query parameter; the field-qualified POST form can return 400. For public analytics, live records expose `firstApplicantName`, `applicantBag`, `examinerNameText`, `groupArtUnitNumber`, and prosecution events even when summary documentation omits examiner fields. Application numbers are stored/searchable as digit-only strings even when displayed as `NN/NNNNNN`; strip the slash for exact filters. `firstApplicantName` queries work for applicant searches, while nested `assigneeBag.assigneeNameText` queries may return no matches. Broad text queries produce false positives but their `firstApplicantName` facet can discover legal-name aliases (including acronym expansions such as IBM). Search facets and filtered `count` queries provide complete aggregate totals without downloading every matching record. Associated grant metadata exposes the XML download under `fileLocationURI`, and that URL may redirect before returning the grant XML. Grant XML may nest multiple `claim-text` elements inside one claim, so claim parsing must collect every descendant text node in order. The current ODP assignments endpoint is keyed by a known application number (`/api/v1/patent/applications/{applicationNumberText}/assignment`); it is not an assignee-name search endpoint.

**Why:** The public USPTO documentation describes both GET and POST search access, but the live endpoint behavior, searchable fields, and associated-document field names are stricter than the generic examples. The first `claim-text` element is only the opening paragraph for many claims. Assignment retrieval also requires candidates seeded by a search that supplies application numbers; it cannot discover unrelated patents globally by party name.

**How to apply:** Keep identifiers and applicant names normalized locally; remove the slash from application numbers in ODP query filters while preserving the conventional slash in user-facing labels. If applicant facets produce multiple plausible legal entities, ask users which names belong in scope instead of silently combining them. Use facets/counts for totals and trends rather than counting a capped page sample. Filter issued records by `patentNumber` and `grantDate` for recent-grant counts; explicit inactive status facets do not establish that the remaining grants are in force. Pace and retry requests because parallel aggregate queries can trigger ODP 429 responses. Follow redirects for `fileLocationURI`, recursively collect all claim descendant text, and treat missing grant XML, claims, or outcome coverage as incomplete rather than inventing metadata. For assignments, use the known-application endpoint and clearly disclose any candidate-coverage limit.
