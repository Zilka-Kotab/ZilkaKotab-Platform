Intended portal architecture

Authentication and authorization must be treated separately.

Microsoft Entra will establish who the user is. Our application's own database will determine whether that person is authorized and what they are permitted to access.

A successful Microsoft login must NEVER automatically grant access to the portal.

There should be no public Sign Up, Create Account, or Register functionality on the website.

Users must first be created/authorized by a Zilka-Kotab ADMIN in our application's database.

After Microsoft authentication, the server should match the authenticated Microsoft identity against an active authorized-user record in our database. If no matching active authorized user exists, access must be denied.

Three application roles

CLIENT

A client sees only the tools and projects specifically assigned to that client/client organization.

ATTORNEY

An attorney has the same tool/project functionality but can switch between separate client areas for each client specifically assigned to that attorney.

ADMIN

An admin has the attorney functionality plus an Admin Portal for managing users, roles, client organizations, attorney/client assignments, tools, projects, and access permissions.

Authorization must be enforced server-side on every protected resource. Hiding frontend elements is not sufficient. Users must not be able to access unauthorized clients, tools, or projects by manipulating URLs, IDs, API requests, or request payloads.

External client users are required

Zilka-Kotab attorneys and administrators will generally have @zilkakotab.com Microsoft 365 accounts.

However, CLIENT users will generally be outside Zilka-Kotab and may use Microsoft accounts belonging to other organizations.

The authentication architecture therefore needs to accommodate authorized external client users while still preventing public/self-service portal enrollment.
